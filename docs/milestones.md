## Ablation experiments

Each ablation changes one thing and keeps everything else the same as the final model. All are scored on validation by the training freeze on Mon 2 Nov, then run once on the test sets on Tue 3 Nov. Every row reports success within 10 mm with a 95% Wilson interval over 3 training seeds, so a gain can be told apart from noise.

| Ablation (brief question) | Baseline | Improved approach | Where the difference shows | How to explain the improvement | Priority |
| --- | --- | --- | --- | --- | --- |
| DART noise (data quality) | BC on clean expert demonstrations only | BC on demonstrations where Gaussian noise is added to the executed action but the clean expert action is stored as the label | T1 success and final error; largest gap on the T3 mid-episode push | Clean demonstrations cover only the expert's narrow path, so one small policy error lands in states the model never saw (covariate shift). DART places recovery states, with the expert's corrective action, around that path. Support it with a histogram of how far training states sit from the expert's path, with and without noise. | Must |
| DAgger (data quality) | π₀: MLP trained on the first expert dataset only | MLP after 4+ DAgger rounds, where the expert relabels states the learner itself visited | Validation success per DAgger round; T1 and T2 success | DAgger trains on the states the policy actually reaches, so training and test state distributions match. Ross et al. show this cuts error growth from quadratic to linear in the episode length. Name the π₀ failure modes that disappear, such as overshoot or stalling near the target. Include an equal-data control: BC trained on the same total number of expert samples. Without it, the gain could just be more data. | Must |
| Data quantity | 500 expert episodes | 2,000 expert episodes (also 1,000) | Learning curve of validation success against episode count | More episodes cover more of the target workspace, until the curve flattens. Compare its slope with the DAgger curve: if one DAgger round adds more success than 500 extra expert episodes, the bottleneck is where the data comes from, not how much there is. | Should |
| Base frame vs world frame (extra input data) | Target and base pose given in the world frame | Target expressed in the robot's base frame, plus sin/cos of the bearing error | T2 workspace grid and randomised start poses | In the world frame, the same reach looks different at every base position, so the network must learn the rotation itself. In the base frame, identical reaches look identical, so the mapping is simpler and generalises to unseen start poses. | Should |
| Derived features (extra input data) | Raw state: `base_pos`, `base_bearing`, `q_mes`, `qd_mes`, `TARGET_EE_POS` | Raw state plus end-effector error from forward kinematics and a phase flag (drive vs reach) | Final error (mm) and success; time to reach | Without FK the network must learn the arm's geometry to know how far the hand is from the target. The EE error hands it that distance directly, which matters most in the last 10 mm. The phase flag separates the two behaviours, driving and reaching, that the policy must switch between. | Should |
| Single state vs history (temporal interval) | Single state at each step | Last 5 states stacked as input | T1 success; torque smoothness; T3 sensor-noise cases | Expected result: no gain, because the expert is Markovian and the current state is enough. History adds inputs and can make the policy copy its own past actions (causal confusion, de Haan et al.). If history does help, the likely cause is noisy velocity readings, which the T3 noise cases test. Either outcome is a justified answer to the brief. | Should |
| Near-target sample weighting (training method) | Every sample weighted equally | Samples within a few cm of the target weighted up | Final error and success; time to reach should barely change | Most samples come from driving and coarse reaching, but success is decided in the last few cm. Weighting focuses the loss where the 10 mm criterion is judged. | Should |
| Network size (architecture, efficiency) | MLP 2×128 | MLP 3×256 (also 4×512) | Success vs parameter count and inference ms per step | Report the smallest model on the plateau. Extra capacity helps until the data runs out, then only adds memory and latency. This row answers the brief's efficiency question with numbers. | Should |
| Model selection rule (evaluation method) | Checkpoint with the lowest offline validation loss | Checkpoint with the highest closed-loop validation success | Rank correlation between loss and success across checkpoints | Offline loss weights every timestep equally and ignores compounding errors, so the lowest-loss checkpoint is not always the one that reaches the target. Show the scatter plot of loss against success. | Should |
| ACT vs MLP (architecture, temporal interval) | Best MLP | ACT: predicts chunks of 10–20 future actions with temporal ensembling | Success, torque smoothness, parameters and inference ms | Predicting chunks of actions shortens the effective decision horizon, which reduces compounding error, and smooths torques. The cost is more parameters and latency. Report both sides of the trade-off. | Could |
